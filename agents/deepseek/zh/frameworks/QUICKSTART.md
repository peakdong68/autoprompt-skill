# QUICKSTART——框架上手通道

你手上有一个任务。这套框架生态会把该任务路由到恰好一个具名的工作流，而你则逐步遵循该工作流。流程并不由你设计——你要做的是挑出正确的框架、打开它的文件、并遵照它的编号步骤行事。本页就是那条上手通道：用三步把你从“我有一个任务”带到“我正在遵循正确的框架”。

---

## 三步上手通道

1. **SELECT。** 运行 `frameworks/README.md` §3 中的 SELECTOR RUBRIC。自上而下走完它，FIRST MATCH WINS。它会交给你恰好一个框架名。
2. **OPEN。** 打开 `frameworks/<that-framework>.md`（例如 `backend-fix.md`）。
3. **FOLLOW。** 自上而下执行它的编号步骤，服从它列出的每一个 if/else 场景。就是这样。

---

## 实战示例

任务：“修复 API 中的一处崩溃。”运行 §3 选择器 → STEP 1c（服务器逻辑 → `backend`）→ STEP 2d（有东西坏了）→ 框架名 **`backend-fix`**。打开 `frameworks/backend-fix.md`，遵循其步骤：把崩溃复现为红灯、根因定位、修复、以绿灯证明。它的工作流判定完成之时，即为完成。

## 14 叶一览（名称 → 何时使用）

- **`apply`** —— 要做什么（WHAT）已被完整指定（冻结规格、“到处把 X 改名为 Y”、脚手架、配置、依赖升级）：应用它、diff 评审、证明绿灯。没有 plan 门禁。
- **`backend-fix`** —— 后端行为损坏：复现红灯、根因定位、修复、以绿灯证明。
- **`backend-implement`** —— 新增/修改一个有界的后端能力（端点、规则、作业），并附带测试。
- **`backend-build`** —— 从零构建一个全新的后端组件/表面，包括接线。
- **`frontend-fix`** —— UI/客户端行为损坏：复现红灯、根因定位、以绿灯证明。
- **`frontend-implement`** —— 新增/修改一个有界的 UI/客户端部件，附带测试 + 可用性检查。
- **`frontend-build`** —— 从零构建一个全新的 UI 表面/流程。
- **`frontend-review`** —— 多画像实地站点评审：N 个真实用户画像访问正在运行的应用，逐步截图，把缺陷/视觉/UX/文案/客户参与度方面的发现汇入一份去重后的工件；P0/P1 问题作为 fix 通道回流。没有浏览器时，降级为带标注的静态走查。
- **`polish`** —— 对既有可用表面做视觉/文案/细节打磨（间距、状态、微文案、响应式）；与 `frontend-review` 的发现配套。
- **`refactor`** —— 保持行为不变的结构重组：先写特征测试，再重塑 + 清除死代码，并证明行为零变化。
- **`plan-scope`** —— 把使命转化为划定范围、按依赖排序的功能拆解/路线图。
- **`plan-research`** —— 通过真实的带凭证研究（research-with-receipts）找到/定义一个 UNKNOWN 目标（论点 + 入围清单）。
- **`plan-design`** —— 为一个 KNOWN 目标产出架构/设计决策（供构建框架消费的蓝图）。
- **`docs`** —— 文档类交付物（README/API 文档/指南）：受众分析、对照代码的准确性验证、一个能跑起来的示例。

## 两条绝不可违反的铁律

1. **严格照办（FOLLOW LITERALLY）。** 完全按照书面写法执行所选框架的编号步骤及其 if/else 场景。不许即兴发挥、重排或跳过。框架就是契约——不多一分，不少一分。
2. **阻塞不变量（THE BLOCKED INVARIANT）。** 遇到任何阻塞，立即停止：报告尝试过程 + 具体的解锁路径，并把裁决向上回传给你的派发方——绝不伪造通过，绝不捏造证据，绝不在检查为红或无法运行时宣布 DONE，绝不向用户屈服。每个叶子都逐字带有这段约 5 行的不变量；请遵照执行。
