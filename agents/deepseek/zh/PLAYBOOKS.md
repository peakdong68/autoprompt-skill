# 分解与操作手册（playbooks）

每个路线图条目都有三个相互独立的轴：

1. **类别（Category）** —— `plan`、`backend`、`frontend`、`data`、`integration`、`infra` 或 `docs`。
2. **可选的操作手册标签（playbook tag）** —— `debug`、`research`、`user-facing`、`polish` 或 `external-target`。
3. **层级（Tier）** —— `T0` 琐碎、`T1` 有界、`T2` 功能，或 `T3` 高远。

类别定义所有权，标签改变规划或验证的执行方式，层级是深度上限。框架叶子声明实际的门禁路径。这三个轴彼此不可替代。

## 有用优先的 scope

新运行没有单独的 intake 往返。在不存在受信任启动证明时，第一位有用路线图作者会验证 RUN/READ/WRITE，检查仓库，划分 scope，选择框架，并撰写可执行的 `ROADMAP.md`。

- **有界（Bounded）：** 一位路线图作者，随后独立评审者与盲测新鲜验证者并发执行：3 个智能体，2 轮。
- **多表面（Multi-surface）：** 保留作者的完整路线图与证据，并发运行恰好两名互补侦察员，然后评审者与新鲜验证者并发执行：恰好 5 个智能体，3 轮，不做冗余的普通综合调度。
- **超大（Unusually large）：** 只有当 `ROADMAP.md` 记录了具体升级理由时，才允许超过 6 个智能体。

核算只覆盖有用的 scope 工作者。运行时编排不增加专门的 preflight、intake 或 scope-coordinator 往返。

只有当需要当前外部事实时才运行外部研究。纯仓库内的工作不支付研究往返成本。被否决的路线图保留已接受的侦察证据，只修复点名的条目。

## 可执行路线图

`ROADMAP.md` 是范围、分解、框架与通道的唯一事实来源。每个条目记录：

- id、标题、category、可选 tag、相称的 tier 与所选框架叶子；
- 负责边界、依赖关系、启动分组与集成通道；
- 实现步骤与正向验收标准；
- 不愉快路径与需要先写的测试；
- 真实验证指令；
- >=95% 变更行与触及模块覆盖率要求；
- 仅当确实还需要一轮设计时才设置 `requiresDetailedPlan`。

可直接实现的条目直接派发到实现阶段。G1 只用于 debug/depth-lock 工作、显式的未决设计分叉、`requiresDetailedPlan: true`，或工作者报告的 `PLAN-CONFLICT`。

框架选择是硬性门禁。缺失或未知的框架属于无效派发。选择器落空时，先经过框架生成与验证，再进入实现。

## 层级阶梯

| 层级 | 形态 | 默认深度 |
|---|---|---|
| **T0** | 显而易见的机械变更 | roadmap item -> implement -> review + verify -> goal-check |
| **T1** | 一个有界变更 | roadmap item -> implement -> review + verify -> goal-check |
| **T2** | 连贯的多文件功能 | 仅在需要时有条件规划 -> implement -> review + verify -> sign-off -> goal-check |
| **T3** | 高远的多功能使命 | 可执行路线图 -> 有条件的逐条目规划 -> 完整构建/验证 -> 清扫收敛 -> goal-check |

框架可以声明更精简的序列。GOAL-CHECK 始终是通用下限。工作者可以返回 `OUT-OF-SCOPE`，触发一级升级；绝不降级。

## 所有权与并行度

拆分到每个路线图条目都拥有真实且互不相交的边界为止。只要独立部分需要接线集成，集成本身就是一个独立条目。把使命分解成每一条真正互不相交的通道；绝不要把多表面使命坍缩成一个"有界"通道。

- 相互独立的条目共享一个启动分组，并在运行时允许时并发执行。
- 依赖关系产生更晚的启动分组。
- 同类的同目标编辑应归入一次批量实现，而不是一次编辑一个智能体。
- 功能内部相互独立的部分可以在边界互不相交时扇出。
- 单薄、重复或递归的扇出是无效的。

使用能抓住该工作真实失效模式的最少门禁，以及依赖图所允许的最大诚实并行度。

## 紧凑派发信封

精确任务只在 `PROMPTS.txt` 中存储一次。后续简报只包含：

- 角色与目标；
- 负责边界与依赖关系；
- 正向验收标准；
- 任务指针（含规范路径、SHA-256 哈希、UTF-8 字节长度与 RUN-NONCE）；
- 经哈希的路线图章节与证据指针；
- 输出模式；
- 真实的模型与 effort 状态。

不要粘贴完整任务、完整路线图、对话记录、教条、先前评审或实现者的主张。工作者行动前要阅读并验证指针。不匹配即为 `INVALID-BRIEF`。

绝不要 spawn 读转发智能体：协调者自己读取所需文件。路线图与计划的规模保持与变更规模相称。

新运行的治理恰好就是 `PROMPTS.txt`、`ROADMAP.md` 与只追加的 `GATELOG.md`。治理文件位于任务目标仓库之外的运行治理根目录：这三个文件绝不写入目标工作树，也绝不出现在其 diff 中。不得创建仅用于治理的 `BRIEF.md`、`PLAN.md`、`AGENTS.md`、`COVERAGE.md`、`BACKLOG.md`、`ANCHOR.md`、`bucketlist.md`、`intake.md`、`scope-map.md` 或按角度拆分的文件。显式恢复运行时旧文件仍可读。

## 操作手册标签

### `debug`

对每一个 debug 功能，在修改生产代码之前必须证明问题为 RED。记录一个可证伪的根因假设以及至少两个竞争成因，其中一名调查员被明确指示："修复不在症状层 —— 找到决定行为的那个函数。"这是强制的深度下限（DEPTH FLOOR）。G1 与新鲜的深度验证都是强制的。修复有证据支撑的最深成因。验证必须证明复现补丁前 RED、补丁后 GREEN，且被触及模块或直接依赖方零 green-to-red 回归。

### `research`

仅在使命要求发现或选定某个目标时使用。用实时凭据研究变化中的外部事实，对选项排序，并把选定的方向绑定进 `ROADMAP.md`。不要创建第二个私有 scope，也不要重复路线图保障已接受的研究。

### `user-facing`

通过真实的用户界面进行验证。在相关时演练代表性视角：首次使用者、高级用户、无障碍访问、怀疑型评估者以及受限设备。把实质性发现转化为点名的路线图修复或实现发现；不要制造角色表演（persona theater）。

### `polish`

定义该工件专属的质量标准，构建后独立评判，修复点名的缺陷并重新评判，直到适用的签核标准通过。相互矛盾的美学发现交由仲裁处理，由仲裁冻结一个符合使命的标准。

### `external-target`

检查真实的外部系统，选择可扩展且测试安全的集成路径，尊重认证/限流/成本/条款约束，并针对真实目标或经验证的契约夹具做端到端验证。绝不用玩具式的本地演示替代所请求的外部行为。

## 闭环失败

失败的评审或验证、签核失败、清扫 P0/P1 或 NOT-DONE 的目标检查，都会重新进入所属路线图条目或创建一个有界的 debug 条目。已接受的证据得以保留。修复只针对点名的失败。仲裁可以在安全且推进使命的选项之间抉择，但不能豁免未关闭的 P0/P1、覆盖率下限或要求的真实验证。
