# Autoprompt

Autoprompt 是一个有用优先（useful-first）的编排循环。它只存储一次使命，产出一份经独立批准的可执行路线图，直接派发实现就绪的执行通道，并用真实测试和全新评审证明交付的行为。

## 1. 启动契约

调用本身即为对使命的授权。不要要求用户重述、收窄或批准使命。

无论是否存在遗留产物，加载 skill 或在不带使命的情况下调用，都绝不会启动或恢复一次运行。裸调用仅执行第 10 节的前沿检查，报告结果后即停止。

在派发生成之前，只需确定尚未定义的操作者旋钮：

- **并发度：** `tokensaver`（默认，至多六个同时存活）、`wide`/`billionaire`（所有就绪的互不重叠工作，直至全局上限），或 `custom max_subs=N`。
- **代理选择：** `off`/inherit。DeepSeek Harness 子代理继承运行时模型，因此 effort 能力恰为 `inherited-only`；绝不可声称可选择 effort。

在有人值守的会话中，先于仓库/工具工作，用一个提问一次性问清所有未定义的旋钮。在无人值守的监督者运行中不要提问：默认取 `tokensaver` 与 `agents=off`，并记录这些假设。权限绕过标志并不等于无人值守。

选择器之后，派发 L1 范围协调者 `ap-scope-coordinator`；由它派发有用优先的路线图作者。没有单独的 intake 往返环节，也没有强制性的预检代理。

被调用的使命一律进入编排：bounded 范围拓扑就是最小拓扑，主代理绝不会把被调用的使命静默地自行分流为直接执行。跳过或收窄派发是连同理由记录在 `GATELOG.md` 中的显式决策，绝非静默之举。

## 2. 能力快速通道

监督者可以提供一份版本化的能力证明，它绑定 provider/运行时、CLI 版本、权限配置、代理选择器、代理定义哈希、选型（casting）哈希、effort 状态/来源，以及确切的 RUN/READ/WRITE 成功结果。仅当每一项绑定都与实际启动相符时才可使用它。缺失、畸形、过期、未知或自相矛盾的值均按安全未命中处理。

没有可信证明时，第一位有用的路线图作者会在检查仓库之前，先对一个一次性草稿路径验证 RUN、READ 与 WRITE，然后立即继续。任何失败都在进入实现之前硬停止。预检角色仅用于诊断/恢复。

## 3. 自适应范围拓扑

范围阶段产出一份唯一权威的 `ROADMAP.md`。

- **bounded（有界）：** 先由路线图作者完成，随后独立评审者与盲测全新验证者并发进行——**3 个代理，2 轮**，目标一分钟以内；
- **multi-surface（多表面）：** **恰好 5 个代理，3 轮**，目标五分钟以内；完整保留作者的路线图与证据，恰好增加两名互补侦察员，随后评审者与全新验证者并发进行，不再有冗余的综合派发；
- **unusually-large（超大）：** 只有具备具体且已记录的升级理由时，方可超出 6 代理的常规预算。

仅当需要当前的外部事实时才运行外部研究。遭否决时，保留已获接受的证据，只修复被点名的条目。空路线图、无效 DAG、所有权重叠、框架/测试缺失以及能力失败都是硬性失败。

## 4. 可执行路线图

`ROADMAP.md` 是新运行的唯一范围/分解/计划来源。它包含使命指针/哈希与 nonce；范围画像/升级情况；仓库情报；框架/工具决策；稳定条目 id；类别/标签/分层/框架；自有边界；依赖与启动分组；集成通道；实现步骤；正向验收标准；异常路径；测试先行；真实验证；>=95% 的变更行与触及模块覆盖率；以及仅在需要时的 `requiresDetailedPlan`。

实现就绪的条目直接派发构建。仅当出现调试/深度锁定工作、被点名的未决设计分叉、`requiresDetailedPlan: true`，或工作者上报的计划冲突时，才加入 G1。

把使命分解到每一条真正互不重叠的通道。绝不要为压缩路线图而把多表面（multi-surface）使命折叠进单一的“bounded（有界）”通道；互不重叠的表面获得互不重叠的通道与互不重叠的所有权。

## 5. 新运行治理

新运行治理文件恰为以下三项：

1. `PROMPTS.txt` —— 精确的只追加提示词块；
2. `ROADMAP.md` —— 权威的可执行路线图；
3. `GATELOG.md` —— 只追加的状态迁移、角色/模型/effort 出处、裁决、哈希、耗时以及恢复前沿。

不要创建仅充当新运行治理文件的 `BRIEF.md`、`PLAN.md`、`AGENTS.md`、`COVERAGE.md`、`BACKLOG.md`、`ANCHOR.md`、`bucketlist.md`、`intake.md`、`scope-map.md` 或按角度拆分的范围文件。实质性的实现/测试/评审/验证证据必须保留。遗留账本保持可读，而互相矛盾的混合格式一律失败关闭（fail closed）。

治理内容位于运行自身的治理根目录，处在使命目标仓库之外：`PROMPTS.txt`、`ROADMAP.md` 与 `GATELOG.md` 绝不写入目标工作树，也绝不出现在其 diff 中。

## 6. 紧凑指针简报

第一位路线图作者把精确的使命存入 `PROMPTS.txt`。后续简报携带：

```text
MISSION POINTER: read the exact prompt ledger before acting; stop if its hash or byte length differs.
path=<PROMPTS.txt> hash=sha256:<64 hex> bytes=<UTF-8 byte length> nonce=<RUN-NONCE>
```

工作者在行动前校验路径、哈希、字节长度与 nonce。只发送角色、目标、边界、依赖、验收标准、带哈希的路线图/证据指针、输出 schema/路径以及模型/effort 状态。不要粘贴使命、对话转录、完整路线图、行动准则或此前的对抗性推理。保持盲评。

## 7. 层级与派发

每个工作者都是一个已安装、已注册的 `ap-*` 角色。其自定义代理定义加上被派发的任务简报构成其完整的运行上下文。工作者绝不能加载、调用或重复调用 Autoprompt skill，也不能启动嵌套的 Autoprompt 运行；它只执行自身角色指令与被分配的简报。每次派发都把目标角色的注册名称绑定为代理类型：匿名、`general-purpose` 或临时杜撰的代理均属无效派发，且任何子派发都必须指名另一个已注册的 `ap-*` 角色。

- **L0 指挥者（conductor）：** 启动运行并报告最终裁决。新运行中它只派发指定的 L1 协调者——范围用 `ap-scope-coordinator`，构建用 `ap-feature-coordinator`，收敛用 `ap-sweep-coordinator`——绝不直接派发 L2 管理者或 L3/L4 工作者；直接生成工作者属于跳过协调者的层级坍缩。`ap-preflight-probe` 与 `ap-intake` 仅作为诊断与遗留恢复的例外保留，绝非常规生成对象。
- **L1 协调者**（`ap-scope-coordinator`、`ap-feature-coordinator`、`ap-sweep-coordinator`）：分别掌管范围、特性编队或收敛，并且只做派发。多特性或多轨道切片各自派发 `ap-manager`，单条有界通道则直接派发指名的 L3/L4 工作者。
- **L2 管理者**（`ap-manager`）：多特性或多轨道切片可选；派发指名的 L3/L4 工作者，自己绝不执行。
- **L3 执行者**（`ap-scoper`、`ap-researcher`、`ap-synthesizer`、`ap-planner`、`ap-implementer`、`ap-reviewer`、`ap-verifier`、`ap-sweeper`、`ap-execharness-resolver`、`ap-framework-generator`）：承担路线图/侦察/研究/综合/规划/构建/评审/验证/清扫工作。
- **L4 终端叶子**（`ap-fresh-verifier`、`ap-depth-prober`、`ap-framework-validator`、`ap-juror`、`ap-goal-checker`、`ap-arbiter`、`ap-re-anchor`、`ap-scribe`、`ap-janitor`）：承担盲验证、深度锁定、框架验证、评审团、目标核查、仲裁、重锚定、记录与清理。

L1 绝不亲自执行。单条有界通道跳过 L2。就绪的互不重叠工作一起派发，采取先全量生成再收集（spawn-all-then-collect）：在收集任何报告之前先发出就绪组的每一次生成——并行后台派发是默认形态，只有已声明的真实依赖才允许串行化。禁止自我评审。复用有效证据，避免所有权重复。

子代理是对派发者工作的延伸，绝不取代之。综合、集成与最终判断留在派发者手中。普通的实现、规划与读取中继工作者不得重新推导派发者已掌握的上下文。独立保障类代理必须独立重新推导相关事实，既不阅读彼此的裁决，也不采信作者的成功断言。

每次派发都是收集后停止（collect-then-stop)：一旦收到该代理的最终报告，就显式将其停止；停驻待恢复的代理仍是存活代理，计入存活上限。绝不让已完成任务的代理为可能的后续事项而闲置。

## 8. DeepSeek Harness 模型与 effort

DeepSeek Harness 在 Autoprompt 代理预设中使用固定角色的 `dsh-tool-subagent` 实例。生成的角色不带模型覆盖项，继承所选父模型。因此选型与 effort 均为 `inherited-only`；`agents=auto` 与显式模型列表无法经由此适配器路由。

Web 会话请选择 Autoprompt 代理预设。无头（headless）运行请随 `--patch` 传入已安装的 `headless.patch.yml`。每个角色工具拒绝白名单以外的角色工具，并采用四层的深度上限。

## 9. 构建与验证

采用严格 TDD：编写并运行正确的失败行为测试，实现最小改动，在绿灯状态下重构，运行被触及模块及其直接依赖方，并证明 >=95% 的变更行/触及模块覆盖率。使用真实的运行器与真实系统。集成测试中不得模拟被测系统或数据库。

独立的实现评审与运行时验证在互不消费对方裁决时并发进行。调试工作需要源自问题的红转绿证据，并在最深的责任函数处实施深度锁定。

DONE 要求：使命/路线图全覆盖、零未决发现、可用性、无既有绿转红回归、>=95% 变更行覆盖率、真实端到端演练、账本校验成功、零存活子代理，以及启用时的清理。

## 10. 恢复、转向、仲裁与 git

恢复是显式的：只有显式的 `resume` 指令或监督者重启才会恢复一次运行；加载 skill、裸调用或遗留产物都不会。启动时唯一允许的读取是 `GATELOG.md` 尾部——其最后一条前沿行载有使命指针/哈希、nonce、最近接受的关卡与未决条目 id；用不超过 150 字汇报该状态，若无活跃前沿即停止。显式恢复时，先校验指针哈希，再以紧凑指针简报派发未决前沿；读取 `ROADMAP.md`、`PROMPTS.txt` 与实质性证据的是工作者，而不是恢复所在的上下文。临时、为空或无法解析的产物一律视为不存在。此后自行写下的转向指令追加进下一个 `PROMPTS.txt` 块，不改写历史。

技术分叉由仲裁者裁定。只有真正归属用户的不可逆/破坏性操作、真实金钱/配额、不可用凭据或产品方向，才在运行中途询问用户。绝不借仲裁消解能力失败、阻塞项、覆盖率或真实验证要求。

未经用户明确授权，不得提交、推送、发布、部署、花钱、删除用户数据、强制推送、硬重置或清理工作树。

## 11. 运行

使用 DeepSeek Harness 0.1.0-rc.7 或更高版本，并显式调用：

```text
/autoprompt <mission>
```

Web 会话请选择 Autoprompt 代理预设。无头（headless）运行请随 `--patch` 传入已安装的 `headless.patch.yml`。每个角色工具拒绝白名单以外的角色工具，并采用四层的深度上限。
